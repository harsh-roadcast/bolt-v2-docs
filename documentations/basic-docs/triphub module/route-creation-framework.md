## Route Creation Framework

Route creation should use the following step-based workflow:

Admin-defined Route Type configuration must determine which route creation steps are shown, skipped, optional or mandatory. For example, if Haltpoint Selection is disabled for a route type, the haltpoint selection step should be skipped and the route must rely on service area/path or another approved route definition method.

- Basic Information
- Select Haltpoints
- Route Definition
- Service Area Setup
- Review Routes


### Current route-builder behavior

The deployed route builder uses the same core step model and includes these additional implementation details:

- The user can select haltpoints from a tabular view with filters, row selection and per-row actions.
- Route configuration supports service type assignment at the route or haltpoint level, including pickup, drop and exchange-oriented setups.
- Configuration captures operational constraints such as load, time expectations, travel distance and sequencing parameters where supported.
- Review combines table data and map preview so the user can verify route geometry, haltpoint ordering and service details before creation.
- Service area creation can be reached from the route builder and supports drawing/choosing an operational zone on the map.
- Final route review must make validation errors visible before allowing route creation.

The workflow must support three route creation modes:

- **Manual Route:** user selects haltpoints and defines route/service rules manually.
- **Auto Route:** system generates routes based on selected haltpoints, service type, load and constraints.
- **Service Area Route:** user defines an area and the trip operates inside the area, with or without predefined haltpoints.

### Basic Information

User should define:

![Manual route basic information](../.gitbook/assets/manual-route-filters.png)

*The first route step captures the route identity and route-type context before haltpoint selection.*

- Route name.
- Organisation / hierarchy scope.
- Territory where applicable.
- Route type.
- Service type rules.
- Scheduler entry point only where the user wants to schedule the route; TripHub must not configure recurrence inside Basic Information.

### Select Haltpoints

User should be able to:

![Manual route haltpoint list](../.gitbook/assets/manual-route-list-view.png)

*List view supports filters, persistent multi-selection, and haltpoint-level operational data.*

![Manual route haltpoint map](../.gitbook/assets/manual-route-map-view.png)

*Map view uses the same selection state and allows spatial review before continuing.*

- Search haltpoints.
- Filter haltpoints by territory/geofence/service area.
- Filter haltpoints by linked/unlinked route status.
- Use list view and map view.
- Select one or multiple haltpoints.
- See selected haltpoint count.
- Review haltpoint details before moving to route definition.

### Route Definition

User should be able to define:

![Auto-route configuration](../.gitbook/assets/auto-route-configuration.png)

*Auto-route configuration captures vehicle, distance, duration, speed, capacity, and route-generation constraints.*

- Sequence or non-sequence based route behavior.
- Service type per haltpoint or route: pickup, drop, exchange.
- Route load and service request totals.
- Start and end logic.
- Estimated distance and estimated time.
- Validation errors before final review.

Additional business rules:

- Automated routes may group haltpoints based on vehicle capacity, load, maximum distance, service window and optimisation constraints where the backend supports it.
- Frequency-generated duplicate service requests must be visible in route review so users understand why a target appears more than once.
- Route review should distinguish between target master records and repeated service requests generated by frequency.

### Exchange service handling

For route types that support Exchange service:

- The system must capture both pickup and drop-side handling.
- If a target is marked as Exchanged, the replacement/drop-side target or item must be captured in the same service flow where required.
- Picked exchange items, such as collected bins/assets, should move into an inventory state instead of remaining linked to the original haltpoint for future route planning.
- Exchange-specific inventory behavior should be visible in reports and audit logs.

### Service Area Setup

Service area setup should support:

![Service-area route setup](../.gitbook/assets/service-area-route-setup.png)

*Service-area planning combines the selected operational data with a spatial preview.*

- Manually create area/path.
- Select existing geofence.
- Upload KML.
- Validate that selected haltpoints are inside or compatible with the selected service area.
- Warn or block when haltpoints do not match the selected area based on route type rules.

### Review Routes

Review screen should show:

![Route review](../.gitbook/assets/route-review.png)

- Route ID.
- Haltpoints count.
- Service request count.
- Service type summary.
- Route load.

- Estimated completion time.

### Route-mode step matrix

Different route modes do not share the same step requirements. The route builder must render steps based on route type and selected creation mode.

| Step | Manual Route | Auto Route | Service Area Route | Notes |
|---|---:|---:|---:|---|
| Basic Information | Mandatory | Mandatory | Mandatory | Route name, organisation, route type, territory where applicable. |
| Select Haltpoints | Mandatory unless route type disables haltpoints | Mandatory for current auto-route design | Optional/unavailable based on route type | Auto-route uses selected haltpoints as input. |
| Route Definition | Mandatory | Replaced by Configuration | Optional | Manual route sequence and service details. |
| Configuration | Unavailable | Mandatory | Optional | Auto-routing field model and strategy. |
| Service Area Setup | Mandatory/optional based on route type | Unavailable in latest Auto Route copy | Mandatory for service-area route | Auto Route copy explicitly says service area cannot be defined. |
| Review | Mandatory | Mandatory | Mandatory | Must show route geometry, counts, validation and creation action. |

Rules:

- The UI must not show Service Area Setup inside Auto Route when the selected auto-route configuration does not support service-area definition.
- A route type can make a step mandatory, optional, skipped or unavailable.
- Step labels and helper copy must reflect route type and business terminology.
- Attempting to continue without required inputs must show inline validation at the field and step level.

### Manual-route haltpoint selection interaction contract

Haltpoint selection must behave predictably across search, filters, pagination and map/list switching.

Rules:

- Filters use additive AND logic.
- Selections persist across search, pagination, filters and list/map switching.
- Changing filters must not clear already selected haltpoints.
- `Unlinked` currently means not linked to any existing route. Whether it should mean not linked to any active route remains an open decision.
- Territory filtering must work even if the territory has no map boundary, using organisation/hierarchy metadata.
- Territory/geofence polygons display only when spatial boundary data exists.
- Continue is disabled until at least one haltpoint is selected.
- Map polygon/circle drawing in this step is a temporary selection tool, not a saved geofence, unless the user explicitly saves it in Service Area/Geofence creation flow.
- The system must distinguish between Select Current Page and Select All Filtered Results.
- View Selected, Clear Selection and selected-count behavior must be available.
- Selection state must survive route-builder step navigation until the user cancels or clears selections.
- Operational filter must support Pickup, Drop and Both where service types are enabled.

States:

- Loading haltpoints.
- No results for current filters.
- No unlinked haltpoints.
- Map failed to load.
- No boundary data for selected territory/geofence.
- Empty state for no eligible haltpoints.
- Partial data loaded with retry.

### Auto-routing field-level requirements

Auto Routing Configuration must capture an explicit field model rather than generic optimisation settings.

| Field | Type | Required | Default | Unit | Validation / constraints | Tooltip intent |
|---|---|---:|---|---|---|---|
| Vehicle Categories | Multi-select | Yes | Empty until user selects | NA | Must select at least one active category. | Select which vehicle categories can be used for generated routes. |
| Start Point for Each Route | Location selector | Yes | Empty until user selects | NA | Must resolve to coordinates or known hub. | Defines where each generated route begins. |
| End Point for Each Route | Location selector | Yes | Empty until user selects | NA | Must resolve to coordinates or known hub. | Defines where each generated route ends. |
| Average Duration | Number | Yes | User-filled during route creation | Hours | Must be a positive number. Exact limits should follow backend validation. | Expected service duration used for planning. |
| Average Distance | Number | Optional | User-filled during route creation | km | Must be zero or positive where provided. Exact limits should follow backend validation. | Expected distance threshold for generated routes. |
| Average Vehicle Speed | Number | Yes | User-filled during route creation | km/h | Must be a positive number. Exact limits should follow backend validation. | Used to estimate travel time. |
| Sweep Radius | Number | Optional | User-filled during route creation | km or m | Must be a positive number where provided. Exact limits should follow backend validation. | Controls spatial grouping radius. |
| Number of Vehicles by Category | Number per vehicle category | Yes | User-filled during route creation | Count | Positive integer per selected category; availability validation depends on selected fleet pool. | Tells optimiser how many routes can be generated per category. |
| Capacity of Each Vehicle | Number per vehicle category | Yes | User-filled during route creation | kg / unit configured | Must be greater than 0. | Limits load per generated route. |
| Maximum Vehicle Range | Number | Conditional | User-filled during route creation | km | Required for EV/range-constrained vehicles if retained. Must be positive where provided. | Prevents generated route from exceeding operational range. |
| Service Hubs / Landfills | Multi-select / location selector | Conditional | Empty until user selects | NA | Required for waste or hub-based operations. | Determines intermediate or terminal service locations. |
| Number of Zones | Number | Optional | User-filled or system-recommended | Count | Positive integer where provided. Exact limits should follow backend validation. | User-defined zone count when not using recommended zone count. |
| Recommended Zone Count | System calculated | Read-only | Calculated | Count | Must show calculation state and fallback. | Shows recommended zone count based on selected data and constraints. |

Supported routing strategies:

| Strategy | Use case | Notes |
|---|---|---|
| K-Means Clustering | Group haltpoints into roughly balanced clusters. | Good for spatial clustering but must be validated against road network and capacity. |
| Voronoi Partitioning | Divide service area into nearest-hub/nearest-zone regions. | Useful when hubs/landfills or depots define operational ownership. |
| Grid-Based Clustering | Divide service area into grid cells for operational batching. | Useful for dense city zones and predictable sweep planning. |
| Road Network Optimisation | Optimise actual road travel sequence and ETA. | Requires routing engine and map-service response. |
| Pre-assigned Zones | Use existing territory/zone assignment as route grouping input. | Useful for customers with fixed operational zones. |

Auto-routing states:

- Loading configuration state and any saved user inputs.
- Validating selected haltpoints and vehicle categories.
- Generating routes in progress.
- Partial success: some routes generated, some haltpoints unassigned.
- No feasible route: constraints prevent valid route generation.
- Backend timeout: generation did not complete within allowed time.
- Retry available after failure or timeout.
- Invalid configuration: missing required fields, non-positive numeric values or backend validation failure.
- Review state with generated route alternatives and unassigned items.

Generated output must show route count, zone count, assigned/unassigned haltpoints, estimated load, estimated distance, estimated time, selected strategy and validation warnings.
